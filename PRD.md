**Date:** September 28, 2026
**Owner:** Isac Artzi, SenSym LLC
**Status:** Approved for build

## 1. Summary

SenSym Job Explainer is a free, open-source Streamlit app that turns a job posting into an explanation a student can act on. The student pastes a job description (or a URL to one) into a single box in the middle of an otherwise empty page and clicks one button. The page then *blooms*: fourteen short, focused panels open outward from the posting, each answering one question a student would ask a mentor — what is this job, what skills does it take and where would I have picked them up, what is the company really looking for, who does this work and how do I reach them, what does the path look like, where is this job going in five years, and what will it turn into.

The app stores nothing: no database, no accounts, no logging. Students bring their own AI key (Anthropic by default; OpenAI, Gemini, and local Ollama supported) and pay their own model costs. One report can be downloaded as DOCX. The app runs locally from a cloned repo or on Streamlit Community Cloud from the same code.

Two guiding rules. **Say what the posting supports and label the rest as judgment** — the model explains, infers, and forecasts, but never fabricates a URL, a named person, a salary figure, or a statistic. **Make the first ten seconds memorable** — the bloom is the product's signature and is designed to draw a "wow" from a classroom.

## 2. Goals and non-goals

### Goals

1. From "I found a posting" to "I understand this job and what to do about it" in about a minute, with no setup beyond an API key.
2. A landing page with nothing on it but one box and one button, and a reveal that students remember.
3. Output that is honest about its own confidence: facts drawn from the posting are presented as facts; everything else is presented as informed judgment with reasoning.
4. A codebase a student can read in an evening. Adding a new panel must be a one-file change (a prompt file) plus one line in a list.
5. Store nothing, track nothing, and say so plainly.

### Non-goals (v1)

- Tailoring a resume or writing application documents (that is Resume Match).
- Job search, scraping job boards, or tracking applications.
- User accounts, history, or saving explanations server-side.
- Personalizing to the student's own background (v1 is generic; see EXTENDING.md).
- Tests, CI, Docker, custom Streamlit components with a Node build step.

## 3. Users

Primary: any student or early-career job seeker looking at a posting and wondering "could this be me, and what would it take?" GCU students are the first audience; nothing is GCU-specific. Secondary: the student-developer who clones the repo to learn from it or add a panel. Tertiary: an instructor projecting it in class.

## 4. Run modes

| | Local | Streamlit Community Cloud |
|---|---|---|
| How it runs | `git clone`, `pip install -r requirements.txt`, `streamlit run app.py` | Open the public URL |
| Config | `job_explainer.env` at repo root auto-loads if present; otherwise upload it or fill the form | Upload or form; held in session memory only |
| Local LLM (Ollama) | Supported | Not reachable from the cloud (documented) |
| Output | DOCX download | DOCX download |

Unlike Resume Match there are no input or output folders, so there is no mode detection. The only difference between the two modes is whether Ollama is reachable.

## 5. Inputs

### 5.1 The posting

One text area accepts either of the following. The app decides which by pattern (a single line matching `^https?://\S+$` is a URL; anything else is text).

- **Pasted text.** The whole posting, any length up to a cap (about 15,000 characters; longer input is truncated with a notice).
- **A URL.** Fetched with `requests` and reduced to readable text with `beautifulsoup4` (drop `script`, `style`, `nav`, `header`, `footer`; keep the largest block of paragraph text). Many job sites (LinkedIn, Workday, Greenhouse behind login, Indeed) block fetching or serve dynamic pages. If the fetch fails or returns fewer than about 400 characters of text, the app shows one friendly line — "That site didn't let me read the posting. Paste the text instead." — and puts the cursor back in the box. URL fetching is a convenience, not a promise; the README says so.

No other input. No file upload in v1 (a posting saved as PDF can be copy-pasted). No "about you" field.

### 5.2 Config file (`job_explainer.env`)

Same `.env` style as Resume Match, generated by an in-app form and downloadable for re-upload. Uploaded config is parsed into `st.session_state` and never written to disk on the server.

```
# --- AI provider ---
LLM_PROVIDER=anthropic          # anthropic | openai | gemini | ollama
API_KEY=                        # leave blank for ollama
MODEL=                          # optional; provider default used if blank
OLLAMA_BASE_URL=http://localhost:11434   # ollama only

# --- Generation (all optional) ---
PARALLEL_CALLS=4                # panels generated at once; use 1 for ollama
READING_LEVEL=                  # e.g. "first-year undergraduate" (default) or "high school"
```

Provider defaults are pinned in one dict in `llm.py`, exactly as in Resume Match; check current provider docs before pinning. Ollama is reached through its OpenAI-compatible endpoint.

## 6. The fourteen panels ("petals")

Each panel is one model call with its own plain-text prompt in `prompts/petals/`. The number prefix is the panel's position in the bloom (see §8). Every panel receives the posting text plus the shared job analysis from §7 step 2, and returns Markdown.

| # | Title | What it answers | Shape |
|---|---|---|---|
| 01 | What this job is | A plain-English explanation of the role in three or four sentences: what the person actually does, for whom, and why the company needs it. | Prose |
| 02 | Skills you'll need | The key skills the posting asks for, each with why it matters here and where someone would realistically have acquired it (a course, a project, a job, a hobby, a certification). | Table: Skill · Why it matters · Where you'd get it |
| 03 | Experience and how to show it | The experience the posting requires or implies, and for each, concrete ways a candidate demonstrates it — in a resume bullet, a portfolio piece, an interview story. | Bulleted pairs |
| 04 | Between the lines | What the company is really looking for in the ideal candidate: reading the tone, the ordering of requirements, the "nice to haves," the team description, and what is conspicuously absent. Labeled as inference. | Prose + short list |
| 05 | Learn more about this job | How to go deeper: the kinds of resources (professional bodies, well-known reference sites such as the BLS Occupational Outlook Handbook and O*NET, subreddits and communities by name, books by topic, the company's own engineering/blog pages if named in the posting). Only names, never invented URLs. | List |
| 06 | Find the people who do this | How to find professionals in this role and reach them respectfully: LinkedIn search phrasing, alumni networks, meetups and conferences by name, and a short template message for an informational interview. No named individuals. | List + template |
| 07 | Similar jobs | Adjacent titles that use most of the same skills, how each differs, and where such postings are typically found. | Table: Title · How it differs · Where to look |
| 08 | The path to get there | The typical educational and professional route: degrees or programs, certifications that matter, the sequence of roles that leads here, and a realistic time frame. Alternative and non-traditional routes included. | Ordered steps |
| 09 | Outlook, 3–5 years | A realistic outlook for this job and its close relatives: demand, drivers, headwinds, what the posting itself signals about the company's trajectory. Explicitly framed as judgment as of the model's knowledge, with a pointer to verify against current BLS data. | Prose |
| 10 | What this job becomes | Which roles and career paths are likely to absorb, replace, or grow out of this job, and what this job will probably morph into. Names the forces (automation, consolidation, new tooling, regulation) behind each guess. | Prose + list |
| 11 | AI and this job | Which tasks in the posting AI tools will likely absorb, which they will amplify, and what a candidate does to be the person who directs the tools rather than competes with them. | Three short lists |
| 12 | Jargon decoder | Every acronym, tool name, and insider phrase in the posting, decoded in one line each. | Table: Term · Meaning here |
| 13 | A week in this job | What a typical week looks like: meetings, deliverables, tools, who you talk to, what "good" looks like at the end of the week. Inference, labeled. | Prose |
| 14 | Questions to ask, things to check | What the posting leaves unsaid (level, compensation, location and remote policy, team size, reporting line), red flags if any, and the questions a candidate should ask a recruiter. Salary is discussed only if stated in the posting or clearly labeled as a general range with the kind of source. | Two lists |

Panel order is deliberate: the four most-asked questions (01–04) sit closest to the posting, discovery and path (05–08) form the next ring, and future-looking and practical panels (09–14) form the outer ring.

## 7. Processing pipeline

Everything runs in memory per session. Prompts are plain-text files.

**Step 1 — Ingest.** Detect text vs URL; fetch if URL; normalize whitespace; truncate to the cap.

**Step 2 — Job analysis (one call, JSON).** `prompts/job_analysis.txt` extracts: title, company (or "not stated"), location and work arrangement, seniority, sector, must-have and nice-to-have requirements, tools and keywords, tone cues, and a one-line summary. This structured analysis is passed to every panel so they agree with each other and with the posting.

**Step 3 — Panels (fourteen calls, Markdown).** Each `prompts/petals/NN_*.txt` prompt receives the posting and the analysis. Calls run in a `concurrent.futures.ThreadPoolExecutor` with `PARALLEL_CALLS` workers (default 4, so a hosted model finishes in roughly 20–40 seconds; Ollama users set 1). Results are collected in panel order. A failed panel does not fail the run: its card shows a one-line error and a "Try again" button.

**Step 4 — Honesty rules (in every prompt, not a separate pass).** No invented URLs (name the resource; do not link it). No named individuals. No specific salary figures unless present in the posting. Facts from the posting stated as facts; everything else labeled as inference or judgment in the panel's own words ("The posting doesn't say, but…"). Reading level per `READING_LEVEL`, default first-year undergraduate. No emoji. Plain Markdown only: headings no deeper than `###`, bullets, bold, and pipe tables — nothing the DOCX renderer cannot handle.

**Step 5 — Render.** The fourteen panels plus the analysis are held in `st.session_state` as one dict. `render.py` converts that dict to a single DOCX report and to `explanation.json`.

Fifteen calls per posting. A cost line ("about $0.0X with the default model — an estimate") appears beside the button, using the same approach as Resume Match's `cost.py`.

## 8. User interface — the bloom

Single page, light only, Notion-style: white, near-black text, one muted accent, generous whitespace, no emoji, Streamlit chrome hidden. Brand tokens live in `job_explainer/ui.py`, copied from Resume Match so the two apps look like siblings.

**Built with plain Streamlit plus CSS.** No custom component, no iframe, no JavaScript beyond what Streamlit ships. Animation is CSS keyframes injected once via `st.markdown`, targeted at containers created with `st.container(border=True, key="petal-NN")` (Streamlit ≥ 1.39 adds a `st-key-petal-NN` class to such containers). This keeps the "pip install only" rule and keeps the code readable.

### 8.1 State A — the seed

The page opens almost empty. Vertically centered in the viewport (as close as Streamlit allows): a small SenSym wordmark, the app name, one line — "Paste a job posting. Understand the job." — a single text area about 12 lines tall with placeholder text "Paste the full job description, or a link to it…", and directly beneath it one primary button: **Explain this job**. To the right of the button, in muted small text, the cost estimate and the privacy line ("Nothing you paste is stored.") Nothing else. No sidebar.

Two quiet affordances, both in muted text and both easy to miss on purpose: a **Settings** link in the top-right corner that opens an `st.popover` (or, if popover proves awkward, an expander that appears below the button) containing the config form and config upload/download; and a **Try an example** link under the box that fills it with one of the sample postings from `examples/`.

If the student clicks Explain with no key configured, the Settings popover opens with a one-line hint instead of an error banner.

### 8.2 State B — growing

On click, the text area is replaced by a compact **seed card** in the same spot: the posting's first line (or the fetched page title) in the card, with a subtle pulse animation and a status line that updates as work happens — "Reading the posting…", then "Growing 5 of 14 panels…". The status is driven by a `st.status` or `st.empty` placeholder updated from the main thread as futures complete. Nothing else is on the page yet. This state lasts 20–40 seconds on a hosted model.

### 8.3 State C — the bloom

When all panels are in, one rerun draws the full layout: a **3 × 5 grid** with the seed card in the exact center cell and the fourteen panels around it, arranged so that the most important panels are nearest the center.

```
┌────────────────┬────────────────┬────────────────┐
│ 09 Outlook     │ 10 Becomes     │ 11 AI & job    │   ring 3
├────────────────┼────────────────┼────────────────┤
│ 05 Learn more  │ 01 What it is  │ 06 The people  │   ring 2 · ring 1 · ring 2
├────────────────┼────────────────┼────────────────┤
│ 02 Skills      │ ★ SEED CARD    │ 03 Experience  │   ring 1 · seed · ring 1
├────────────────┼────────────────┼────────────────┤
│ 07 Similar     │ 04 Between     │ 08 The path    │   ring 2 · ring 1 · ring 2
├────────────────┼────────────────┼────────────────┤
│ 12 Jargon      │ 13 A week      │ 14 Questions   │   ring 3
└────────────────┴────────────────┴────────────────┘
```

Each panel is a bordered container of fixed height (about 320 px, `st.container(height=320)` so long content scrolls inside the card and the grid stays a grid), with the panel title as a small heading and the Markdown beneath. Tables render as Streamlit Markdown tables.

**The animation.** Every panel container carries a CSS class for its ring. Keyframes take each panel from `opacity: 0; transform: scale(0.55) translate(dx, dy)` — where `dx, dy` point toward the center cell, so panels appear to fly outward from the seed — to `opacity: 1; transform: none`, over about 600 ms with an ease-out curve. `animation-delay` is 0 ms for ring 1, 220 ms for ring 2, 440 ms for ring 3, with a further 60 ms stagger within a ring so no two panels move in lockstep. The seed card itself does a brief settle (scale 1.06 → 1) as the first ring appears. Total choreography about 1.3 seconds. `prefers-reduced-motion` disables the transforms and keeps a simple fade.

Because Streamlit reruns the script on every interaction, the animation classes are attached only on the first render after generation completes (a `just_bloomed` flag in session state, cleared at the end of that run). Later interactions — scrolling a card, clicking a button — render the grid without animation so it never replays unasked.

**The seed card in State C** is the control hub: job title and company (from the analysis), location and seniority on a second line, then three small actions — **Download report (.docx)**, **Read as a page**, and **Start over**. "Read as a page" toggles a single-column view in panel order 01–14 for reading or projecting; the toggle label becomes "Back to the bloom." "Start over" clears everything including the key (per the privacy promise) and returns to State A.

Each panel has a small muted **Regenerate** control in its corner that re-runs that one prompt and swaps the card content in place with a short fade. (Should, not Must — see §11.)

At widths below about 900 px Streamlit stacks the columns; the order then reads top to bottom as the grid rows, which keeps the seed card in the middle of the page. Acceptable for v1; the design target is a projector or laptop at 1024 px and up.

Accessibility basics: real labels on every control, sufficient contrast, headings in order, nothing conveyed by color alone, focus visible.

## 9. Output

One DOCX, `job_explainer_<slug>.docx` (slug from title and company), rendered with `python-docx` in the same clean style as Resume Match's `docx_style.py`: title block (job title, company, date), a "Posting summary" section from the analysis, then the fourteen panels in numeric order as level-2 headings. The Markdown-to-DOCX conversion handles paragraphs, `###` headings, bulleted and numbered lists, bold and italic, and pipe tables — nothing more, and the prompts are constrained to that subset. `explanation.json` (analysis plus all panel Markdown) is offered as a second, secondary download.

## 10. Privacy and data handling

Identical to Resume Match: no database, no server-side writes (a `tempfile` only if DOCX assembly needs one, deleted immediately), API key in `st.session_state` only, no `st.cache_*` on user content, `gatherUsageStats = false`, no analytics. The only network calls are to the chosen model provider and, if the student pastes a URL, to that URL. The README repeats the key-hygiene advice (limited-spend key, rotate after use) and notes that the model provider processes whatever the student pastes.

## 12. Non-functional requirements

Bloom complete within about 45 seconds on a hosted model with four parallel calls. Runs on macOS, Windows, Linux with `pip install` only; no system binaries. Every module under about 300 lines; adding a panel is one prompt file plus one entry in the `PETALS` list in `pipeline.py`. All user-facing text at a first-year undergraduate reading level. Usable at 1024 px and up; presentable on a projector.

## 13. Technical design

**Stack.** Python 3.11+, Streamlit ≥ 1.39, python-docx, requests, beautifulsoup4, python-dotenv, anthropic, openai (also Ollama), google-genai.

**Repository layout.**

```
SenSym-Job-Explainer/
├── app.py                      # Streamlit entry point; layout and state machine only
├── job_explainer/
│   ├── config.py               # load / validate / generate job_explainer.env (port from Resume Match)
│   ├── ingest.py               # text-or-URL detection, fetch, clean, truncate
│   ├── llm.py                  # complete() / complete_json() over four providers (port from Resume Match)
│   ├── pipeline.py             # PETALS list, job analysis, parallel panel generation
│   ├── render.py               # panels dict → DOCX report + explanation.json
│   ├── cost.py                 # rough cost estimate (port from Resume Match)
│   └── ui.py                   # brand tokens, CSS incl. bloom keyframes, seed card, petal card helpers
├── prompts/
│   ├── job_analysis.txt
│   └── petals/
│       ├── 01_what_it_is.txt
│       ├── 02_skills.txt
│       ├── … one file per panel …
│       └── 14_questions.txt
├── examples/                   # three sample postings as .txt (fictional companies)
├── .streamlit/config.toml      # light theme, usage stats off
├── job_explainer.env.example
├── requirements.txt
├── README.md
├── EXTENDING.md
├── PRD.md
├── CLAUDE.md
└── LICENSE                     # MIT
```

**The `PETALS` list.** One place in `pipeline.py` defines each panel as a small tuple: `(number, slug, title, ring, grid_cell)`. `app.py` lays out the grid from it, `pipeline.py` loads `prompts/petals/{number}_{slug}.txt` from it, and `render.py` orders the DOCX from it. A student adds a panel by adding a prompt file and one tuple (and, if the grid is full, widening it).

**Threads and Streamlit.** Worker threads only call `llm.complete()` and return strings; no Streamlit calls happen off the main thread. The main thread waits on `as_completed()` and updates the status placeholder.

**Ported modules.** `llm.py`, `config.py`, `cost.py`, and the DOCX styling helpers are copied from Resume Match and trimmed (drop vision/image support, drop folder fields). Keep the docstrings; students read both repos.

## 14. Delivery plan

**Demo build.** State A → B → C with all fourteen panels on Anthropic; the bloom animation; DOCX download; config form; three example postings; README. Regenerate-per-panel and the cost line may be stubbed with a `# TODO(v1.1)`.

**v1.0.** Fill stubs, verify OpenAI/Gemini/Ollama, deploy to Streamlit Community Cloud, share with students.

**Demo script (five minutes).** Open the empty page. Click "Try an example." Point at the privacy line. Click Explain. Talk for thirty seconds about what the app is doing. Watch the bloom. Open "Skills you'll need" and "Between the lines." Toggle "Read as a page." Download the DOCX and open it. Then open the repo, show `prompts/petals/04_between_the_lines.txt`, and say: "Add a file here and you have a fifteenth panel."

## 15. EXTENDING.md — seed ideas for students

Presented as invitations with the module each touches and a rough difficulty.

- An optional "about you" line that personalizes the path, skills, and outreach panels, with a diff view of what changed.
- A fifteenth panel of the student's own design (the recipe in §13), e.g. a five-question self-check or a "compensation reality check" grounded in a public dataset the student chooses.
- Compare mode: two postings side by side, panels aligned, differences highlighted.
- A real bloom: replace the CSS reveal with a custom Streamlit component that lays the panels out radially with force-directed spacing.
- Save the explanation to the student's own Google Drive or Notion (their credentials, their storage).
- A "skills constellation": a graph of the skills across every posting a student has explained this session.
- Voice mode: read the panels aloud, or let the student ask a follow-up question about any panel.
- Small-model mode: prompt engineering so an 8B Ollama model produces acceptable panels, with a scorer to prove it.
- A classroom mode: instructor pastes one posting, students see the bloom on their own devices via a share code (needs a tiny server — a good systems project).
- Evaluation harness: a set of postings and rubric-based scoring of each panel for honesty (no invented URLs or figures) so prompt edits can be measured.

## 16. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Model invents URLs, people, salaries, or statistics | Honesty rules in every prompt; "name it, don't link it"; inference labeled; README says to verify |
| Outlook and "what it becomes" panels are stale relative to the model's knowledge | Panels state that they are judgment as of the model's training and point to BLS / O*NET for current data |
| URL fetching fails on most job boards | One-line fallback to paste; README explains; the box accepts both so nothing else changes |
| Fifteen calls feel slow | Parallel execution; status line with a panel count; the seed pulse shows life |
| Animation replays on every rerun | `just_bloomed` flag; classes attached only on the first post-generation render |
| Streamlit version drift breaks `st.container(key=…)` styling | Pin `streamlit>=1.39`; fall back to a wrapping `st.markdown` div if the class hook ever disappears |
| Student pastes a key into a public app | Session-only handling, HTTPS, README guidance on limited-spend keys |
| Very long postings blow the context | 15,000-character cap with a notice |
| Grid looks cramped on small screens | Columns stack below ~900 px; design target is 1024 px+ |
